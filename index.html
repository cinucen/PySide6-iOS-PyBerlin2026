Why iOS is different

  • No system Python: the interpreter and the standard library ship inside the app
  • No loading code at runtime: an app can only run what was signed into it
  • Everything is built, signed and launched through Xcode
  • Simulator and device are different targets, so different binaries
  • Desktop: pip install PySide6 and run python
  • iOS: no pip on the device, no Python installed
    • Interpreter, standard library, Qt and PySide6 all packaged inside the app bundle
    • Layout defined by the Python community's iOS support (PEP 730), and we follow it
  • Simulator and real device are different targets, so different binaries
    • Why we have one set of wheels per target later

On iOS it all becomes one program

PySide6 is Python on top of compiled C++.

Desktop and Android

The compiled parts stay separate files, loaded when you import them.

iOS

They are merged into one program file when you build it.

Apple does not allow loading them separately.

Decided at build time, not at import time.

  • PySide6 = Python on top of compiled C++
  • Desktop and Android
    • Compiled parts stay separate files, loaded when you import them
    • Both ship everything inside the app, nothing downloaded at runtime, but the pieces stay separate
  • iOS
    • Merged into one program file when you build the app
    • Apple's rule: an app may only run code that was part of it when it was signed
    • No way to keep the pieces separate and load them later
  • So: decided at build time, not at import time
  • Proper terms, if asked
    • Desktop and Android: dynamic linking (shared libraries, .so files)
    • iOS: static linking (archives merged into the executable)
    • Qt for iOS ships static libraries only
    • Qt for iOS with shared libraries is possible, but has its own problems and makes the steps more complex
  • Nothing to load at import time, so every module has to be registered with the interpreter before it starts

Two stages

1. Build the wheels
  • Cross-compile PySide6 for one target
  • Slow, done rarely
2. Deploy your app
  • pyside6-ios-deploy
  • Fast, done every time

Same shape as Android

  • If you know the Android deployment, this feels the same; deploying to iOS is just as easy
  • Two stages
    • First: the heavy cross-compilation, separate from the everyday tool that turns your app into a project
    • One target = one platform and architecture: arm64 device, arm64 simulator, x86_64 simulator for Intel Macs
  • Wheels: build once per Qt version and target, install once, use across many projects

Stage 1: cross-compile the wheels


  $ git clone https://code.qt.io/pyside/pyside-setup
  $ cd pyside-setup
  $ python tools/cross_compile_ios/main.py \
        --qt-install-path ~/Qt/6.12.0 \
        --arch arm64 --simulator

  dist_ios/pyside6-...-ios_arm64_simulator.whl
  dist_ios/shiboken6-...-ios_arm64_simulator.whl
  • One run per target (device, simulator)
  • The wheel tag records the target
  • The Qt for iOS kit is bundled inside the wheel
  • Slow part: compiles Shiboken and PySide6 against the Qt for iOS kit
  • Needs a Mac, plus Qt for iOS and the matching Qt for macOS
    • The macOS build supplies the host tools used during cross-compilation
  • You choose the CPU architecture and simulator or device
  • Output: a normal wheel with an iOS platform tag, e.g. ios_arm64_simulator
    • Qt kit is copied into the wheel: self-contained, no separate Qt install needed

Stage 2: pyside6-ios-deploy


  $ pyside6-ios-deploy main.py \
        --wheel-pyside   pyside6-...-ios_arm64_simulator.whl \
        --wheel-shiboken shiboken6-...-ios_arm64_simulator.whl

  open deployment/ios_arm64_simulator/pyside_app_demo.xcodeproj
  • App + wheels in, Xcode project out
  • Nothing is compiled; it takes seconds
  • No --simulator flag: the target comes from the wheel's platform tag
  • Settings are kept in pysidedeploy.spec
  • The day-to-day tool: main file + two wheels in, Xcode project out
  • Never compiles anything: takes seconds, rerun whenever your config changes
  • Output goes into a folder named after the target: device and simulator projects don't overwrite each other
  • What you need on your side
    • A Mac with full Xcode (not just the Command Line Tools): project is built with the iOS SDK and simulator runtimes
    • Device build: Apple Developer Team ID via --team-id; simulator: not needed
  • Python.xcframework: downloaded and cached on first run, or pass your own with --xcframework-path
  • The tool never asks for the target
    • A wheel has binaries for exactly one target, so it reads the target from the wheel filename
    • Simulator wheels give a simulator project, device wheels a device project
    • Simulator to device: pass the device wheels, that is all
    • Refuses to continue if the PySide6 and shiboken6 wheels target different platforms
  • Result is an Xcode project: sign and deploy it from Xcode

What gets generated


  // main.mm - generated by pyside6-ios-deploy
  PyImport_AppendInittab("PySide6.QtCore",     PyInit_QtCore);
  PyImport_AppendInittab("PySide6.QtWidgets",  PyInit_QtWidgets);
  PyImport_AppendInittab("shiboken6.Shiboken", PyInit_Shiboken);

  Py_InitializeFromConfig(&config);
  PyRun_SimpleFile(fp, "main.py");
  • main.mm: your imports are scanned → those Qt modules get linked → registered here
  • Info.plist: app name, bundle id, version
  • project.pbxproj: contains what to link, and build phases that copy the standard library and your .py files into the bundle

Open it in Xcode, press Run.

  • Three files generated
  • main.mm
    • Small Objective-C++ entry point: initializes the embedded Python, hands control to your script
    • No QtWidgets .so to import: each module registered as a built-in before the interpreter starts
    • After that, import PySide6.QtWidgets resolves to something already inside the binary
    • Registers every PySide6 module actually linked in, not just direct imports
      • A module can pull in another (QtQml needs QtNetwork)
      • Unregistered module fails at runtime: "could not import module"
    • Qt's dependency graph is read from the .prl files in the kit, not by hand; same way Qt plugins and QML plugins are found and registered with Q_IMPORT_PLUGIN
    • Available modules follow the Qt for iOS kit the wheel was built from
      • Add-ons like Qt PDF can be added to that kit
      • Module missing from the kit: dropped without a diagnostic (see limits slide)
  • Info.plist: app metadata (name, bundle id, version); flags --name, --bundle-id, --app-version
  • project.pbxproj: the Xcode project itself; libraries to link, resources to copy into the app

Python packages on iOS

Pure Python
  • Works if you copy the folder next to your code; data files are not bundled
Packages with compiled code
  • NumPy, Pillow, anything with C inside
  • Same problem PySide6 itself had
  • Not handled by the tool yet

Today the bundle carries your code, PySide6 and Shiboken - nothing else.

  • Question: can I use my favourite package? Two cases
  • Pure Python: just source files
    • Copy the package folder next to your code: bundled and works
    • Not supported yet: declaring it as a dependency
    • Anything that is not a .py file (e.g. data files) is not copied
  • Compiled extensions (NumPy style)
    • Need a wheel built for iOS; a desktop wheel will not work
    • Today the tool copies PySide6 and shiboken6 into the bundle and your .py files to the root, nothing else
    • A C-extension package does not work at all yet
  • Same consequence of static linking: a C-extension package has exactly the problem PySide6 had
  • Why it is the next big piece on the roadmap

Known limits

  • Use the official Qt for iOS kit from the Qt installer:
    • Custom Qt builds are not supported
  • C-extension packages are not supported
  • Wheels are built per target: once for the simulator, once for the device (no universal binary)
  • A Qt module missing from the kit is dropped silently
  • First: official Qt for iOS kit from the Qt installer
    • Custom Qt builds are not supported
    • Deliberate decision: keeps the generated project simple and predictable
    • If you need it, tell us; I can't promise a date
  • Second: packages with C extensions are not supported (seen earlier)
  • Third: wheels are built per target (one for simulator, one for device); no universal binary
  • Easy to trip over: a Qt module missing from the kit is dropped silently, no error message; a real diagnostic is on the roadmap
