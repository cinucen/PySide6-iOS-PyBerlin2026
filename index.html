Qt is a C++ framework that has been around for 30 years. Most people have used a Qt application without knowing it. For example, LG Electronics uses Qt for its smart TV platform webOS, the Sauber F1 team, currently Audi, uses Qt technology for pit stop optimization and driver training, and the iLovePDF app is built with Qt, along with many more.

The same code and the same UI toolkit run on every major platform, including mobile and embedded.

PySide6 is the official Qt binding for Python. It exposes the Qt API, not a subset, so what you read in the Qt docs maps to Python almost one to one.

Shiboken is the generator that reads the Qt headers and produces the binding code. This matters later: that generated code is C++, and for iOS we have to cross-compile it, meaning we build it on the Mac for the phone.

PySide6 runs on Windows, macOS, Linux and Android, and now on iOS as well

Qt has two ways to build a UI. With Widgets, you create the interface in Python code, step by step: a button, a layout, and a signal connected to a function. These are the classic desktop-style controls, which is why they suit forms, dialogs and tools. With QML, you describe how the interface looks in a declarative file, and Python provides the logic behind it. QML is designed for fluid, touch-oriented interfaces with animations.

Both work with PySide6 and both can be deployed to an iOS device. Our demo later is a Widgets app (Tetrix), but QML works as well.

Wheels for the desktop platforms are on PyPI, and Android has been supported for a while through pyside6-android-deploy. So iOS is the one people kept asking about. With version 6.12 it is now possible.

Why iOS is different

  • No system Python: the interpreter and the standard library ship inside the app
  • No loading code at runtime: an app can only run what was signed into it
  • Everything is built, signed and launched through Xcode
  • Simulator and device are different targets, so different binaries

On desktop you pip install PySide6 and run python. On iOS there is no pip on the device and no Python installed. So the interpreter, the standard library, Qt and PySide6 all have to be packaged inside the app bundle. The Python community's iOS support, PEP 730, defines that layout, and we follow it.

Also, the simulator and a real device are different targets, so they need different binaries. That is why we will have one set of wheels per target later.

On iOS it all becomes one program

PySide6 is Python on top of compiled C++.

Desktop and Android

The compiled parts stay separate files, loaded when you import them.

iOS

They are merged into one program file when you build it.

Apple does not allow loading them separately.

Decided at build time, not at import time.

PySide6 is Python on top of compiled C++. On desktop and on Android, those compiled parts stay as separate files, and they get loaded when you import them. Both platforms ship everything inside the app, nothing is downloaded at runtime, but the pieces stay separate.

On iOS, they are merged into one program file when you build the app. That is Apple's rule: an iOS app may only run code that was part of it when it was signed, so there is no way to keep the pieces separate and load them later.

So on iOS it is decided at build time, not at import time. For those who want the proper terms: desktop and Android use dynamic linking, shared libraries and .so files. iOS uses static linking, where archives are merged into the executable. Qt for iOS ships static libraries only. There is a possibility to build Qt for ios with shared libraries but, it has its own problems and making the steps a bit more complex.

Since there is nothing to load at import time, every module has to be registered with the interpreter before it starts.

There are four layers. First, Python for iOS, which is an xcframework distributed by python.org. Second, Qt for iOS, which is the normal Qt kit built for iOS. Third, PySide6 and Shiboken, cross-compiled for iOS as static archives. And on top of that is your application, which stays plain Python.

Nothing here is custom. These are the standard pieces, glued together by our tooling.

Two stages

1. Build the wheels
  • Cross-compile PySide6 for one target
  • Slow, done rarely
2. Deploy your app
  • pyside6-ios-deploy
  • Fast, done every time

Same shape as Android

If you are already familiar with the Android deployment, this will feel the same, and deploying the same app to an iOS device is just as easy.

There are two stages. The first is the heavy cross-compilation, which is separate from the everyday tool that turns your app into a project. One target here means one platform and architecture, so for example an arm64 device, an arm64 simulator, or an x86_64 simulator for Intel Macs.

You build the wheels once per Qt version and target, install them once, and use them across many projects.

Stage 1: cross-compile the wheels


  $ git clone https://code.qt.io/pyside/pyside-setup
  $ cd pyside-setup
  $ python tools/cross_compile_ios/main.py \
        --qt-install-path ~/Qt/6.12.0 \
        --arch arm64 --simulator

  dist_ios/pyside6-...-ios_arm64_simulator.whl
  dist_ios/shiboken6-...-ios_arm64_simulator.whl
  • One run per target (device, simulator)
  • The wheel tag records the target
  • The Qt for iOS kit is bundled inside the wheel

This is the slow part: it compiles Shiboken and PySide6 against the Qt for iOS kit. You need a Mac, and you need both Qt for iOS and the matching Qt for macOS installed, because the macOS build supplies the host tools used during cross-compilation. You choose the CPU architecture and whether the target is the simulator or a device.

The output is a normal wheel, but with an iOS platform tag, for example ios_arm64_simulator. The Qt kit is copied into the wheel, so the wheel is self-contained and your app does not need a separate Qt install.

"Do I have to cross-compile PySide6 myself?"

  • No, stage 1 is not necessary
  • Get the wheels from the Qt Downloads page, or with qtpip 
    
    $ pip install qtpip
    $ qtpip download PySide6 --ios --arch arm64 --platform simulator
  • Install once, use across projects
  • Stage 1 is for whoever builds the wheels, or if you build from source

No. Most app developers only need stage 2. So you can completely forget about it :D Stage 1 is for the people who produce the wheels, so generally us, and anyone who wants to build from source.

Everyone else can get the wheels from the Qt Downloads page, or with qtpip, which is Qt's own pip tool: pip install qtpip, then qtpip download PySide6 with the iOS options.

Stage 2: pyside6-ios-deploy


  $ pyside6-ios-deploy main.py \
        --wheel-pyside   pyside6-...-ios_arm64_simulator.whl \
        --wheel-shiboken shiboken6-...-ios_arm64_simulator.whl

  open deployment/ios_arm64_simulator/pyside_app_demo.xcodeproj
  • App + wheels in, Xcode project out
  • Nothing is compiled; it takes seconds
  • No --simulator flag: the target comes from the wheel's platform tag
  • Settings are kept in pysidedeploy.spec

This is the tool you use day to day. You give it your main file and the two wheels, and it generates an Xcode project. It never compiles anything, so it takes seconds and you can run it every time you change your app's configuration. The output goes into a folder named after the target, so device and simulator projects do not overwrite each other.

What you need on your side: a Mac with a full Xcode installation, not just the Command Line Tools, because the generated project is built with the iOS SDK and the simulator runtimes that ship with Xcode. A device build also needs your Apple Developer Team ID, passed with --team-id. The simulator does not.

Python.xcframework is downloaded and cached automatically on the first run, or you can pass your own with --xcframework-path.

The tool never asks you which target you want. Because a wheel contains binaries for exactly one target, it reads the target from the wheel filename: simulator wheels produce a simulator project, device wheels produce a device project. So to switch from simulator to device, you pass the device wheels, and that is all. It also refuses to continue if the PySide6 and shiboken6 wheels target different platforms.

The result is an Xcode project, so to run the app on your device you sign and deploy it from Xcode.

What gets generated


  // main.mm - generated by pyside6-ios-deploy
  PyImport_AppendInittab("PySide6.QtCore",     PyInit_QtCore);
  PyImport_AppendInittab("PySide6.QtWidgets",  PyInit_QtWidgets);
  PyImport_AppendInittab("shiboken6.Shiboken", PyInit_Shiboken);

  Py_InitializeFromConfig(&config);
  PyRun_SimpleFile(fp, "main.py");
  • main.mm: your imports are scanned → those Qt modules get linked → registered here
  • Info.plist: app name, bundle id, version
  • project.pbxproj: contains what to link, and build phases that copy the standard library and your .py files into the bundle

Open it in Xcode, press Run.

The tool generates three files.

The first is main.mm, the small Objective-C++ entry point that initializes the embedded Python and hands control to your script. There is no QtWidgets .so file to import, so each module is registered as a built-in before the interpreter starts. After that, import PySide6.QtWidgets in your script resolves to something that is already inside the binary.

The tool registers every PySide6 module that is actually linked in, not just the ones your source imports directly. A module can pull in another one transitively, for example QtQml needs QtNetwork, and an unregistered module fails at runtime with "could not import module". Qt's own dependency graph is read from the .prl files in the kit rather than maintained by hand, and that is also how Qt plugins and QML plugins get found and registered with Q_IMPORT_PLUGIN.

The set of modules available to you follows the Qt for iOS kit that the wheel was built from. Add-ons like Qt PDF can be added to that kit. A module that is missing from the kit is currently dropped without a diagnostic, which I come back to on the limits slide.

The second is Info.plist, the app metadata: the app name, the bundle id and the version. You can set them with flags such as --name, --bundle-id and --app-version.

The third is project.pbxproj, the Xcode project itself. It lists the libraries to link and the resources to copy into the app.

Python packages on iOS

Pure Python
  • Works if you copy the folder next to your code; data files are not bundled
Packages with compiled code
  • NumPy, Pillow, anything with C inside
  • Same problem PySide6 itself had
  • Not handled by the tool yet

Today the bundle carries your code, PySide6 and Shiboken - nothing else.

You will probably ask: can I use my favourite package? There are two cases.

Pure-Python packages are just source files. If you copy the package folder next to your own code, it gets bundled and works. What is not supported yet is declaring it as a dependency, and anything in the package that is not a .py file, such as data files, is not copied.

Packages with compiled extensions, NumPy style, need a wheel built for iOS, and a desktop wheel will not work. Today the deploy tool copies PySide6 and shiboken6 into the bundle and your own .py files to the root, and nothing else, so a C-extension package does not work at all yet.

This is the same consequence of static linking as before. A C-extension package has exactly the problem PySide6 had, which is why it is the next big piece on the roadmap.

Known limits

  • Use the official Qt for iOS kit from the Qt installer:
    • Custom Qt builds are not supported
  • C-extension packages are not supported
  • Wheels are built per target: once for the simulator, once for the device (no universal binary)
  • A Qt module missing from the kit is dropped silently

First, you need the official Qt for iOS kit from the Qt installer. Custom Qt builds are not supported. That is a deliberate decision: it keeps the generated project simple and predictable. If you need it, tell us, but I cannot promise a date.

Second, packages with C extensions are not supported, as we saw earlier.

Third, wheels are built per target, so you have one for the simulator and one for the device. There is no universal binary.

And one more that is easy to trip over: if a Qt module is missing from the kit, it is currently dropped silently, with no error message. A real diagnostic for that is on the roadmap.

Your PySide6 app already runs on iOS

  • Same Python, same Qt, same code as your desktop app
  • Two stages: build wheels once, pyside6-ios-deploy every time
  • Everything is linked in at build time: your app can only use the modules built into it

Three things to remember. Your PySide6 app already runs on iOS, with the same Python, the same Qt and the same code as on desktop. The workflow is two stages: build the wheels once, then run pyside6-ios-deploy every time. And the main thing to remember: on iOS everything is linked into the app when you build it, so the modules your app can use are fixed at build time.

Roadmap

  • Qt 6.12 is out; PySide 6.12 ships this support
  • Third-party packages - the big missing piece, and the hard one
  • A real diagnostic when a Qt module is dropped
  • More examples

Qt 6.12 is out, and PySide 6.12 ships this support. What comes next is a real diagnostic for dropped modules, more tested examples, and third-party package support.

Third-party support is the natural next consequence of static linking. A C-extension package has exactly the same problem PySide6 had, so it needs the same treatment: an iOS-built static archive, linked in and registered before Python starts. That is why it is hard, and why it is the headline item.
