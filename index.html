Python on an iPhone

Why iOS is different

  • There is no system Python to rely on: Python must be inside the app
  • Apps cannot load arbitrary native code at runtime the way desktop pip installs assume
  • Everything is built with Xcode and signed by Apple's toolchain
  • Simulator and device are different targets (different binaries)
On desktop, you pip install PySide6 and run python. On iOS there is no pip on the device and no Python installed. So the interpreter, the standard library, Qt and PySide6 all have to be packaged inside the app bundle. iOS also restricts how native code is loaded, which is why the native libraries are handled specially. Do not go deep into the loader details; if asked, say that the Python community's iOS support (PEP 730) defines the layout, and we follow it. Simulator and device are different CPU/OS targets. This is important later: it is why we have per-target wheels.

The building blocks

  • Python for iOS, from python.org (PEP 730)
  • Qt for iOS
  • PySide6 + Shiboken, cross-compiled for iOS
  • Your app, as plain Python files

Two stages, same shape as Android

1. Build the wheels
  • Cross-compile PySide6 for one target
  • Slow, done rarely
2. Deploy your app
  • pyside6-ios-deploy
  • Fast, done every time

Stage 1: cross-compile the wheels


  $ python tools/cross_compile_ios/main.py \
        --qt-install-path ~/Qt/6.12.0/ios \
        --arch arm64 --simulator

  dist_ios/pyside6-...-ios_arm64_simulator.whl
  dist_ios/shiboken6-...-ios_arm64_simulator.whl
  • One run per target (device, simulator)
  • The wheel tag records the target
  • The Qt for iOS kit is bundled inside the wheel

Stage 2: pyside6-ios-deploy


  $ pyside6-ios-deploy main.py \
        --wheel-pyside   pyside6-...-ios_arm64_simulator.whl \
        --wheel-shiboken shiboken6-...-ios_arm64_simulator.whl

  open deployment/ios_arm64_simulator/pyside_app_demo.xcodeproj
  • App + wheels in, Xcode project out
  • Nothing is compiled; it takes seconds
  • Settings are kept in pysidedeploy.spec

The target comes from the wheel

  • No --simulator flag on the deploy tool
  • It reads the platform tag from the wheel filename
  • Simulator wheels build a simulator project, device wheels build a device project
  • One source of truth, so the two can't disagree

What gets generated

  • main.mm: starts Python and Qt, then runs your main.py
  • Info.plist: app name, bundle id, version
  • project.pbxproj: what to link, and your files to bundle

Open it in Xcode, press Run.

Which Qt modules end up in the app?

  • The tool scans your imports to decide what to link
  • The set available follows the Qt for iOS kit you built the wheel from
  • Add-on modules (for example Qt PDF) can be added to the kit
  • Watch out: a module missing from the kit is dropped without a diagnostic
You do not list modules by hand. The tool looks at which PySide6 modules your code imports. The catch: the modules that can be linked are the ones present in the Qt kit used to build the wheel. Add-ons, for example Qt PDF, are built separately and need to be installed into the kit, and we confirmed Qt PDF works on iOS. Be upfront about the sharp edge: if a module is missing from the kit, it is silently dropped, so the first symptom is an import error at runtime. A diagnostic is a known improvement. Say this plainly.

Status

  • Works: simulator and physical device
  • Works: Widgets apps (Tetrix) and Qt add-ons built into the kit
  • Part of PySide 6.12, with Qt 6.12 already released
  • TODO: App Store submission status, only if you have verified it

Known limits

  • Only the standard framework Qt for iOS kit; custom or non-framework Qt builds are not supported
  • Modules missing from the kit are dropped silently
  • C-extension packages need iOS-built wheels
  • Wheels are built per target, once for the simulator and once for the device

Takeaways

  • Your Python + Qt app can now run on iOS
  • Two stages: build wheels once, pyside6-ios-deploy every time
  • The target comes from the wheel
